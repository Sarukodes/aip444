# Assignment 2 Reflection

## 1. Workflow, Agent, or Hybrid Design

I designed the project as a hybrid system.

Phase 1 and Phase 2 are mostly workflows because the steps are predictable. In Phase 1, the program reads the job PDFs, extracts structured information, researches the company, saves the JSON, and then creates the market analysis. In Phase 2, it extracts my resume, loads the Phase 1 data, compares the resume with the market, and creates the gap analysis.

I used more agent-like behavior when the LLM needed to decide what information to research. For example, company research uses Tavily, gap analysis can perform a focused Tavily search, and the Phase 3 legitimacy check uses Tavily and WHOIS.

Phase 3 is also hybrid. Python controls the overall order of the application, while the LLM handles tasks such as requirement matching, legitimacy reasoning, company research, and application advice.

I decided not to make everything fully agentic because during testing I saw that agents can make too many tool calls if there are no strict limits. I also found that exact values such as job counts and fit percentages are more reliable when calculated using normal Python code.


## 2. Prompt Engineering for Extraction Consistency

The most useful prompt changes were the rules that prevented the model from guessing information.

For job extraction, I told the model to:

- only use information supported by the job posting
- not invent missing information
- use `null` for missing scalar values
- use empty lists for missing list fields
- separate required skills from preferred skills
- preserve salary information as written
- use the current date and PDF capture date when calculating posting age
- not guess education or experience requirements

I also included the current date because some postings use relative dates such as "posted 3 days ago."

Another important choice was using Pydantic structured outputs instead of simply asking the model to return JSON. The response has to match the schema before it is accepted.

This helped during testing because some LLM responses were cut off before the JSON was complete. Pydantic rejected those responses instead of allowing incomplete data to be saved.

Later, I also noticed that repeated runs on the same Celestica posting could classify required and preferred skills differently. This caused the fit score to vary more than I wanted.

To improve this, I set the extraction temperature to `0` and made the prompt more specific about how required and preferred skills should be classified. I also prevented the same skill from appearing in both lists.

After this change, two final Celestica runs both extracted:

- 20 required skills
- 16 preferred skills

The two fit scores were 18% and 19%, which were both classified as Growth Target. This was much more consistent than the earlier runs.

I also learned that some values should not be generated by the LLM at all. For example, an early market analysis incorrectly reported 11 jobs even though I had 10. I changed the implementation so the total number of jobs is calculated directly in Python.


## 3. Legitimacy Agent Design

For the legitimacy agent, I wanted the decision to be based on evidence instead of only the wording of the job posting.

The main tools I used were:

- Tavily web search
- WHOIS lookup

The agent checks signals such as:

- whether the company has a real website and online presence
- whether the company appears in reliable search results
- whether the job can be connected to official company information
- how old the company domain is
- whether contact information matches the company
- unrealistic compensation
- requests for payment
- requests for SIN, banking details, government ID, or other sensitive information
- suspicious communication methods
- artificial urgency
- vague or inconsistent job details

I considered domain registration age an important signal because a company claiming to be established while using a very recently registered domain would be suspicious.

I did not treat WHOIS privacy protection itself as a red flag because legitimate companies can also use private registration.

The final legitimacy output includes:

- GREEN, YELLOW, or RED verdict
- confidence score
- evidence and signals
- recommendation

One limitation is that WHOIS does not always return complete information and can sometimes time out.

For example, the Celestica WHOIS lookup showed a socket timeout during testing, but the tool still returned useful information such as the 1996 registration date and registrar.

Web search also has limitations because companies can have similar names. During the Avant Techno Solutions research, some search results referred to companies with similar names.

Because of this, I would use the legitimacy result as guidance and still manually verify important information before sending personal information to an employer.

Cost also affected some of my design decisions.

During an early Celestica test, the legitimacy agent made too many Tavily searches and the context became very large.

I fixed this by adding hard limits.

The final legitimacy agent uses:

1. one focused Tavily web search
2. one WHOIS lookup

The gap analysis also uses only one focused Tavily search.

This made the runs smaller and more predictable.

## 6. Other AI Tools Used

Besides Codex, I also used ChatGPT during the assignment.

### Where ChatGPT Helped

ChatGPT helped me understand parts of the assignment requirements, debug errors, review outputs, and check whether my evaluation files matched the rubric.

One useful example was the tool-call problem.

Originally, I was limiting the number of agent rounds, but the model could still request many Tavily calls inside one round.

ChatGPT helped me identify that the number of tool calls themselves also needed hard limits.

This led to the final design where gap research uses one focused search and legitimacy uses one Tavily search plus one WHOIS lookup.

ChatGPT also helped me review the consistency problem in the job extractor. This led to setting the extraction temperature to `0` and making the required/preferred skill rules more specific.

### Where AI Output Needed Correction

One example was the market analysis.

The LLM incorrectly reported that 11 jobs had been analyzed when the real number was 10.

It also changed some salary information and made assumptions about currency.

I did not keep that output.

Instead, I changed the program so deterministic information is handled by Python.

For example:

```python
analysis.total_postings = len(jobs)
```

Salary observations are also copied from the extracted data instead of asking the model to calculate or convert them.

Another example was application advice that could have made project experience sound equivalent to professional experience.

I added stronger honesty rules so the final system does not recommend unsupported claims.

## 8. Overall Reflection

The biggest thing I learned from this assignment was that an LLM should not be responsible for every part of an AI application.

The LLM worked well for:

- extracting information from job postings
- finding patterns
- researching companies
- identifying resume gaps
- reasoning about legitimacy
- generating application advice

Normal Python worked better for:

- counting jobs
- calculating fit percentages
- preserving exact salary values
- validating schemas
- controlling agent loops
- limiting tool calls
- handling files

I also learned that agent loops need strong guardrails.

At first, I thought limiting the number of iterations would be enough, but one LLM response could still request many tools. Adding limits directly to the number of tool calls made the system much more predictable.

Another thing I learned was that even with structured output, LLM results can still vary between runs. The Celestica extraction showed this clearly. Making the extraction instructions stricter and using a temperature of `0` improved the final consistency.

I would use this project as a real job-search support tool, but I would not trust every result without checking it.

I would manually verify:

- whether the company is legitimate
- whether the job is actually available
- salary information
- experience requirements
- requests for money
- requests for sensitive information
- major resume claims

Overall, the system became much more reliable after I combined LLM reasoning with deterministic Python logic, added structured validation, limited tool usage, improved extraction consistency, and manually tested the output.
